# W01 and W11 local acceptance evidence

The tests ran on pve-bot on 2026-11-25 with Linux 6.8.0-151-generic, cgroup v2, systemd, and nested KVM available through /dev/kvm. The official smolvm release was 1.37.1, commit 9d3ab4c82756456565544558ac2ea5412afa84ef. The verified Linux x86_64 archive SHA-256 was f8d5d1aaa198c7b9e676fa4365998e22fc9051a2199b208741be5f38fef5e404. [Official release](https://github.com/smol-machines/smolvm/releases/tag/v1.37.1)

## W01 runtime adapter

```sh
SMOLVM_TEST_SOCKET=/run/smolvm-phase1/api.sock \
SMOLVM_TEST_IMAGE_DIR=/var/lib/smolvm-phase1-images \
SMOLVM_TEST_IMAGE=debian-task-gate-base.tar \
go test -v ./internal/runtime/smolvm
```

The Unix-socket response-loss test observed the original runtime name after one Create request lost its response. The identity test marked runtime observations unknown when PID or start time was absent or inconsistent. The live test created, started, executed, paused, resumed, executed again, queried metrics/capacity, stopped, and deleted a fixture. Its original PID/start time was 10232/58869. Resume retained the original native pause ID and reported PID/start time 10324/59131. The direct Docker-save tar booted successfully. A gzip variant in the local runtime returned an upstream crane error while reading the archive manifest.

The pinned runtime can briefly return a pre-dispatch 409 after Resume because its supervisor has not refreshed the detached execution's cached handle. The adapter waits for the public runtime identity to remain stable and retries only the exact native pre-dispatch response. The successful real test ran in 3.83 seconds. [Upstream discovery implementation](https://github.com/smol-machines/smolvm/blob/9d3ab4c82756456565544558ac2ea5412afa84ef/src/api/state/discovery.rs)

After the local test host reboot, the transient serve unit was gone. The persistent `smolvm-phase1.service` recovered the two existing machines as stopped using their original state directories. It listens at `/run/smolvm-phase1/api.sock` with an ACL for the local validation account, and the guest rollout port stays at 127.0.0.1:18081.

## W11 clean install and service survival

The isolated package installed as version 0.1.1 using the bundled managed template and a cached, verified official runtime archive. Management returned HTTP 200 on 127.0.0.1:8443 and the runtime reported readiness. The runtime directory was root:sandbox-control 0770 and the socket was root:sandbox-control 0660. An unrelated account was denied access. The first rehearsal exposed the native per-VM UID traversal requirement for the runtime cache. With umask 0022 and the traversable runtime parent in the unit/installer, the second rehearsal installed from empty platform and runtime directories without manual changes.

```sh
sudo python3 tests/integration/installed.py \
  --password-file /etc/sandbox-platform/owner-password \
  --template "$(jq -r '.[0].template_id' /opt/sandbox-platform/current/templates.json)"
```

The managed task `task_c8cca87ada687eeef2dcc267b240b075` ran in VMM PID 27459/start time 110036, in the native scope `/smolvm.slice/smolvm-vm-sbox_d81fda9f7cd58419d53418db37db2d23.scope`. Both service units used `KillMode=control-group`. The public runtime identity and platform control epoch remained equal across all four events.

| Event | Service PID | Task stdout cursor |

| platformd restart | 25949 → 27551 | 13 → 26 |
| smolvm-serve restart | 25913 → 27569 | 26 → 39 |
| platformd SIGKILL | 27593 → 27647 | 39 → 65 |

After task cancellation, the platform produced signed standalone checkpoint `snap_b0f8c013dd9936f8537ed25b77af9e3d`, 147503457 bytes, SHA-256 6e0d017ce5c027c7438fd0653b1dff30bc445ec978f202cd8a5d31357d27c309. The fixture machine was deleted.

The socket-activated status helper was checked against a disposable created native machine. The installed platform UID received `restart_policy=never` through the fixed root-owned helper. The command used the native runtime state directory and no VM was started.

## Backup, upgrade and rollback

An online `admin backup create` copied the live registry, config, signed manifest and checkpoint. `admin backup verify` accepted the archive. With the writer stopped, maintenance restore saved a rollback copy, replaced the registry and preserved the ready checkpoint. The control epoch changed from c47cab62-83a4-4aea-ab8d-d44e13351958 to 2814c0b9-b453-42f8-be15-14d333fb356c and maintenance stayed active. The automated restore regression additionally confirmed that a queued operation from the old epoch becomes `recovery_required` with unknown effect and that a running writer prevents restore.

The verified release upgraded from 0.1.1 to 0.1.2 in maintenance. A fixture release 0.1.3 whose daemon deliberately exited at startup was rejected and 0.1.2 served HTTP 200 again. Explicit compatible binary rollback to 0.1.1 also returned HTTP 200. The diagnostic ZIP contained the allowlisted report.json with runtime readiness, registry recovery state and host pressure.

The backup rehearsal used a separate local directory on pve-bot. Transfer to a separate failure domain and a cold Host reboot of the installed platform were outside this rehearsal.

Uninstall removed the platform service and CLI link while the runtime service, registry, and checkpoint files stayed available. A 0.1.4 data-preserving reinstall restored access to the same registry and signed artifact. The runtime, status socket, and platform services were active after reinstall. The maintenance exit was explicit. An authenticated Create using the old control epoch returned HTTP 409.
